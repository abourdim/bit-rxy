Critical — silent data loss

1 · correctnessBLE writes are not split to the 20-byte MTU

The micro:bit negotiates the default 23-byte ATT MTU, leaving exactly 20 bytes of payload. A longer write is silently truncated, not rejected — the trailing \n never arrives, the firmware's uartReadUntil(NewLine) waits forever for a line that never completes, and the command vanishes with no error on either side.

This breaks bit-rxy's own built-in widgets:

Widget idExample messageBytesResult
dpad_navSET dpad_nav right 121lost
joy_moveSET joy_move 180 10021lost
slider_speedSET slider_speed 10021lost at ≥100
slider_powerSET slider_power 10021lost at ≥100
editfield_nameSET editfield_name …21lost

The sliders are the nastiest failure mode: they work for values 0–99 and die silently at 100. Testing at low values looks perfect, then it fails in front of an audience. The D-pad and joystick — the two headline widgets — are broken outright.

Fix: in bleWrite(), loop the encoded buffer in ≤20-byte slices and write each one. No firmware change needed — the UART service buffers incoming bytes, so uartReadUntil() reassembles them. The reverse direction already worked because onNotify() reassembles via state.rxBuffer.

Smallest useful change in the whole list. If only one thing gets done, do this one — it makes the D-pad, joystick and sliders work, and carries almost no regression risk.

Critical — the firmware generator ships the same landmines to every user

generateDemoCode() emits the starter firmware for every project built with bit-rxy, so anything wrong in the template is copied into all of them. It currently contains:

2 · correctnessNo pacing between CFG chunks

The generated GETCFG loop writes every chunk back-to-back with no basic.pause() at all. Chunks outrun the BLE connection interval and get dropped — this is the "stuck at 0%" hang, baked into every generated firmware.

for (let i = 0; i < CFG.length; i += 18) {
    bluetooth.uartWriteLine("CFG " + CFG.substr(i, 18))   // <-- no pause
}

Fix: add basic.pause(20) inside the loop, plus one before CFGBEGIN and one after. maqueen-rxy uses 20ms; 35ms is the safe fallback if a device is fussy.

3 · correctnessBlocking calls inside the BLE receive handler

The template calls basic.showIcon(IconNames.Yes) from inside onUartDataReceived. Every basic.show* renders and then pauses — roughly 600ms for showArrow/showIcon, 400ms for showLeds. That blocks the receive callback, so the next command arrives while the handler is still busy and gets dropped or reordered. Template totals: 18 basic.show* calls.

Reference point: DFRobot's own working firmware keeps the display entirely off the command path — every display call there belongs to a dedicated display verb, never to the motor path.

Fix: handlers set a flag; a basic.forever loop does the drawing, passing interval 0 so nothing pauses. One renderer, no races.

4 · correctnessserial.writeLine() in the template (×5)

serial.writeLine() blocks the calling fiber when nothing is draining the USB serial buffer — which is the normal case once the cable is unplugged and the robot runs on BLE alone. It looks fine while debugging with a serial monitor open, then hangs in real use.

Fix: gate all logging behind a debugEnabled flag defaulting to false, and prefer queueing log lines for the main loop to emit over BLE rather than writing to serial at all.

5 · robustnessNo connection flag gating uartWriteLine

The template has no btConnected-style flag, so it keeps writing to the UART after the link drops. Writing to a UART with no peer blocks once the buffer stops draining, which wedges the BLE stack — and a wedged stack makes the next connect hang in service discovery.

Fix: set a flag in onBluetoothConnected / onBluetoothDisconnected and gate every write on it. Also: draw the display before any radio write in the loop, so a wedged radio can't starve the screen.

Reliability — connect/disconnect

6GATT setup can hang forever

getPrimaryService() and friends can never resolve and never reject if the peripheral's GATT server is still holding a previous session. connectBle() then sits inside an await with no error and no way out; clicking Connect again just wedges at the same step.

Fix: wrap each setup call in an ~8s timeout, and disconnect the half-open GATT link in the catch block so the next attempt starts clean.

7Stale disconnect events kill live sessions

Reconnecting calls disconnect() on the previous device; that event can arrive after the new connection is up and wipe it. Guarding on state.ble.device is not enough — it is only assigned after every characteristic lookup, so during setup a genuine drop gets dismissed as stale and resurfaces later as a confusing NetworkError.

Fix: track a currentDevice claimed as soon as requestDevice() resolves, and compare against that.

8Disconnect listeners accumulate

Chrome returns the same BluetoothDevice object for a given device, so addEventListener stacks one handler per connect attempt — a single disconnect then runs the teardown several times.

Fix: remove the previous listener before attaching a new one, and make onDisconnect() idempotent. Add a ~400ms settle delay before reconnecting.

9A dropped GETCFG has no recovery path

If the request is lost, the loader sits at 0% forever — nothing retries.

Fix: resend every ~3s, up to ~4 attempts, cancelled on the first CFGBEGIN or CFG line. Keep the retry window longer than a full transfer, or a retry fires mid-stream and corrupts a perfectly healthy one.

Minor

10D-pad shares one widget id across four directions

All four send under the same id, and the send queue keeps a single latest-wins slot, so a quick direction change can overwrite an unflushed press or release. Less likely once the MTU fix lands, but still a real race.

Fix: a small FIFO for discrete must-not-drop messages, drained ahead of the latest-wins slot (which stays correct for continuous controls like sliders and joysticks).

11Duplicate D-pad binding

btn.onclick = press fires in addition to mousedown, so press() runs twice per tap. Currently harmless only because the dpadPressed guard swallows it — but that same guard, with the 100ms release debounce, silently drops a genuine second tap inside 100ms.

📍 script.js:5978

12No way to disconnect from the app

The header pill always calls connectBle(), so clicking it while connected re-opens the device picker instead of hanging up. Nothing ever drops the GATT link, so the firmware never sees a disconnect.

Fix: make it a toggle — connect when idle, disconnect when live.

Suggested order

  • Ship item 1 alone first. One function, biggest payoff, near-zero regression risk.
  • Then items 2–5 together as a single generator-template update.
  • Then 6–9 as a connect-reliability pass.
  • 10–12 whenever convenient.

All twelve are implemented and field-tested in maqueen-rxy. Copy from there rather than rewriting — the fixes carry explanatory comments about why, which are worth keeping.
